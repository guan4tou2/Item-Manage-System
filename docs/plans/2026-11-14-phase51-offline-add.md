# Phase 51：離線新增物品

- **狀態**：🚧 進行中
- **日期**：2026-11-14
- **基線**：`main` `d3e258e`（Phase 47）；本期於獨立分支進行，與 Phase 48–50（Migration 0030–0032）平行，合併時接在其後
- **來源**：roadmap 候選「Background Sync（離線新增）」

---

## 目標與範圍

在沒有網路的地方（地下室、倉庫、訊號不好的賣場）也能把東西記下來，連線後自動補送。

roadmap 原本寫「IndexedDB 佇列＋SW sync」。本期**刻意收斂**成可以驗證、失敗模式清楚的版本：

- **做**：已經開著 App 時斷線，仍可「新增物品」；資料先存在裝置上，恢復連線後自動同步，不會重複建立。
- **不做**：由 service worker 在分頁關閉後背景同步（Background Sync API 只有 Chromium 支援，且登入 token 存在頁面端、SW 拿不到）。分頁關閉期間不會同步，下次開啟 App 時自動處理。
- **不做**：離線編輯／刪除既有物品（那才有真正的衝突合併問題）、離線上傳圖片、離線使用 AI。

## 設計決策

### 不重複建立（伺服器端）

- **D1 `Idempotency-Key`**：`POST /api/items` 接受選填的 `Idempotency-Key` 標頭（UUID 格式，其他格式 `422`）。同一位使用者以同一個 key 重送時，**回傳第一次建立的那個物品**（`200`，內容同 `ItemRead`），不再建立新的。沒有帶標頭時行為完全不變。
- **D2 資料表 `idempotency_keys`（Migration 0033，接在 0032 之後）**：`owner_id`（FK users，CASCADE）、`key`（char 36）、`item_id`（FK items，CASCADE）、`created_at`；`UNIQUE(owner_id, key)`。key 的寫入與物品建立在**同一個交易**內。並行重送以 unique constraint 收斂：後到者查回既有物品。
- **D3 保留 7 天**：每次寫入時順手刪除 7 天前的紀錄（比照 `login_attempts` 的清理方式）。超過保留期才重送視為新請求——文件明示。
- **D4 物品已被刪除**：key 對應的物品若已軟刪除，重送回 `410 {"code":"idempotent_item_deleted"}`，不重新建立（使用者已經處理過它）。

### 離線佇列（裝置端）

- **D5 儲存**：瀏覽器 IndexedDB（原生 API，不加套件），資料庫 `ims-offline`、store `pending-items`，主鍵為 `client_id`（`crypto.randomUUID()`，同時作為 `Idempotency-Key`）。每筆記錄：`owner_user_id`、表單 payload、後續步驟所需資料（是否啟用批次、自訂欄位值）、`created_at`、`status`（`pending`／`syncing`／`failed`）、`error_code`、`attempts`。
- **D6 依使用者隔離**：佇列項目標記建立者的 user id；只有同一位使用者登入時才顯示與同步。登出不刪除（下次登入會繼續），但登出時若有待同步項目要先提示。其他人在同一台裝置登入看不到、也不會送出別人的項目。
- **D7 什麼時候進佇列**：新增物品送出時，若 `navigator.onLine` 為 false，或請求因**網路層失敗**（fetch 丟出例外、沒有拿到任何 HTTP 回應）而失敗 → 存入佇列。拿到 HTTP 回應的失敗（4xx／5xx）照原本的錯誤處理，不進佇列。
- **D8 離線時不可用的欄位**：圖片上傳與 AI 功能需要連線。離線時表單上這些入口顯示為不可用並說明原因；已經在線上傳好的圖片（已有 `image_id`）會跟著佇列項目保留。
- **D9 同步時機**：`online` 事件、App 載入時、登入成功後、使用者按「立即同步」。同一時間只跑一輪（single-flight），逐筆依建立順序送出。
- **D10 同步一筆＝重放線上的送出流程**：把新增頁現有的送出步驟（建立物品 → 需要時建立第一個批次 → 儲存自訂欄位值）抽成一個函式，線上送出與佇列重放共用，避免兩套邏輯。建立物品時帶 `Idempotency-Key`。
- **D11 失敗分類**：
  - 網路層失敗 → 維持 `pending`，下次再試（不計為錯誤）。
  - `401` → 整輪暫停，等使用者重新登入（`apiFetch` 會先嘗試 refresh）。
  - `403`／`404`／`409`／`410`／`422` 等確定性的錯誤 → 標為 `failed` 並記下 `error_code`，不自動重試；使用者可以「編輯後重送」或「捨棄」。典型原因：離線期間選的分類／位置被刪了、帳號變成唯讀。
  - `5xx` → 維持 `pending`，`attempts` 加一；同一筆連續 5 次後標為 `failed`。
  - 物品已建立但後續步驟（批次、自訂欄位）失敗 → 視為成功移出佇列，另外提示使用者到物品頁補上（與線上流程的既有行為一致）。

### 介面

- **D12 離線提示**：App 外框在離線時顯示一條不搶眼的提示列：「目前離線——新增的物品會先存在這台裝置」。恢復連線即消失。用 `aria-live="polite"` 播報狀態變化。
- **D13 送出回饋**：離線送出後 toast「已存在這台裝置，連線後自動同步」，回到物品清單。
- **D14 待同步區塊**：物品清單頁上方，只在有佇列項目時出現：「N 筆待同步」，可展開看每一筆的名稱、建立時間、狀態（待同步／同步中／失敗＋原因的白話說明）。動作：「立即同步」（整體）、每筆「編輯後重送」（帶著原值開新增表單，送出成功後移除原項目）與「捨棄」（AlertDialog 確認）。
- **D15 同步結果**：成功 → toast「已同步 N 筆」並重新整理物品清單；有失敗 → toast 說明並保留區塊。
- **D16 導覽列徽章**：有待同步項目時，「物品」導覽項目旁顯示數量。
- **D17 狀態**：瀏覽器不支援 IndexedDB 或被停用（私密視窗）→ 離線時送出顯示明確錯誤「這個瀏覽器無法離線保存」，不可靜默遺失資料。儲存空間不足同樣要有訊息。
- **D18 視覺**：離線提示與待同步是中性資訊，用 muted；失敗才用既有的 `--destructive`／`--warning` 語意色（顏色＋文字）。一律走 token。
- **D19 viewer**：唯讀使用者本來就看不到新增入口，不受影響。
- **D20 i18n**：zh-TW／en 同步。

### Service worker

- **D21 不改快取策略**：現有 SW 已對 `/_next/static/` 採 cache-first、對頁面導覽採 network-first 並以快取為後備。也就是「曾經開過的頁面」離線時仍打得開。本期不加預先快取；「從完全沒開過 App 的狀態離線啟動」不在保證範圍，文件明示。

## 實作結果

### 已完成

- API：新增 `IdempotencyKey` model 與 Migration 0033（接 0032），以 `(owner_id, key)` 複合主鍵落實唯一性；物品與 key 在同一交易提交，並行競爭失敗時 rollback 後查回既有物品。重送回 200，軟刪除回 410 與 `idempotent_item_deleted`；每次 keyed 寫入清除七天前紀錄。重送不重新派送 webhook，也不增加稽核紀錄。
- 型別：依指定直譯器從本 worktree 匯出 OpenAPI，再執行 `node generate.mjs`。產物同時補齊本分支原先尚未生成的既有 schema（包含清單分享等）；未修改其實作檔案。
- Web：原生 IndexedDB 儲存介面、依 owner 隔離、共用新增送出函式、single-flight 逐筆同步、重新登入／online／App 載入／手動同步，以及所有 D11 失敗分類。重新開啟 App 會恢復遺留的 syncing 項目；換帳號時停止舊帳號後續送出，接續新帳號輪次。
- 介面：離線 live region、保存與同步 toast、待同步區塊與確認捨棄、桌面／行動導覽徽章、記憶體帶值編輯後重送；編輯中的項目不重放舊值，已捨棄項目也不由同步快照復活。離線停用新增表單圖片上傳與 AI 入口並說明原因；保留既有 image_id。
- 登出：一般登出先讀取佇列，以既有 AlertDialog 提示；登出所有裝置的既有確認框補上待同步提醒。登出不清除 IndexedDB。
- i18n：zh-TW／en 同步；全部新視覺沿用既有 UI 元件與語意 token。
- 測試：API 覆蓋驗證清單、交易競爭與副作用；Web 覆蓋儲存介面、D7、D11、同步時機／single-flight／使用者切換、原線上流程、D17 呈現、編輯／捨棄與登出提示。新增 Playwright 離線成功（桌面／375px）與位置刪除失敗情境。

### 與計畫的差異／釐清

- D2 使用複合主鍵實現 `UNIQUE(owner_id, key)`，不另加流水號。
- 既有線上「自訂欄位失敗」實際行為是顯示失敗 toast 並留在表單，與計畫對既有流程的描述略有不同；為維持線上行為，保留此路徑。佇列重放則依 D11 移出已建立項目，並以 toast 的「前往物品頁」動作引導補填。批次失敗仍沿用原本導向物品頁的行為。
- 未加入背景同步、離線編輯／刪除或任何預先快取；未更動 service worker。關閉分頁期間不會同步；完全未曾開過 App／頁面的離線啟動不保證可用；超過七天保留期的 key 重送會視為新請求。
