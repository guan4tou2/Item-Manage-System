## 現況與問題

收據辨識（Phase 33／38）把一張收據拆成多列草稿，同一張收據以 `receipt_id` 群組，收據層資料是存在每列 `payload.receipt` 的快照，**沒有收據資料表**。佇列的群組標頭依 AI 抽取結果顯示對帳四態（相符／差額／無法判斷／舊資料）。

兩個缺口：

1. **警示關不掉**：AI 讀錯總額或漏讀折扣時，標頭會一直顯示差額警示。使用者拿紙本核對過、確認沒問題，也沒有地方表達。
2. **看不到整張收據**：佇列只列「還沒處理」的草稿。品項一接受就從群組消失，無法回頭看這張收據原本有哪些行、各自後來怎麼了。

## 目標

1. 使用者可以把一張收據標記為「已人工核對」（可附一句備註、可取消）；標記後不再顯示差額／無法判斷的警示。
2. 提供整張收據的檢視頁：收據資訊、算術拆解、**所有**品項行（含已接受、已捨棄）與各自的去向。

## 設計決策

### 資料與 API

- **D1 新資料表 `ai_receipt_reviews`（Migration 0030）**：`receipt_id`（GUID，PK）、`owner_id`（FK users，CASCADE）、`verified_at`（timestamptz，NOT NULL）、`note`（varchar 200，nullable）。**列存在＝已核對**，取消核對＝刪除該列。不改寫草稿的 `payload.receipt` 快照——快照是「AI 當時讀到什麼」的證據，人工判斷另外存。
- **D2 收據的擁有權**：收據沒有自己的表，以「本人名下至少有一列 `receipt_id` 相同的草稿（任何狀態）」判定；否則一律 `404`（不區分不存在與他人的）。
- **D3 端點**（皆在既有 `/api/ai/receipts` 之下；writer guard 與既有 AI 路由一致，viewer `403`）：
  - `GET /api/ai/receipts/{receipt_id}` → 整張收據：`receipt_id`、`snapshot`（取任一列的快照）、`review`（`{verified_at, note}` 或 `null`）、`image_id`（第一頁）、`lines[]`。
  - `PUT /api/ai/receipts/{receipt_id}/review`，body `{note?: string ≤ 200}` → 建立或更新核對紀錄（冪等；重複呼叫更新 `note`、**不**改 `verified_at`），回傳 `review`。
  - `DELETE /api/ai/receipts/{receipt_id}/review` → `204`（原本就沒有也回 `204`）。
- **D4 `lines[]`**：該收據**全部狀態**的草稿，依收據行序（`receipt_item.index`）排序。每行：`draft_id`、`index`、`name`（AI 讀到的名稱）、`quantity`、`unit_price`、`subtotal`（皆為收據上的值）、`status`、`item_id`（已接受時為建立的物品，物品已刪除則為 `null`）。不回傳使用者在卡片上尚未送出的編輯——那些只存在前端表單。
- **D5 佇列帶出核對狀態**：`DraftRead` 新增 `receipt_review`（`{verified_at, note}` 或 `null`；非收據草稿為 `null`），清單端點以一次查詢取回該頁所有 `receipt_id` 的核對紀錄（不逐列查）。純新增欄位。
- **D6 不寫稽核、不進備份**：核對是使用者對自己暫存資料的註記；AI 草稿本來就不在備份範圍內。文件明示。
- **D7 只保留第一頁影像（既有限制，不在本期解決）**：建立收據時每列草稿只存了第一頁的 `image_id`，其餘頁面的對應沒有保留。檢視頁顯示第一頁並標示「共 N 頁，僅保留第一頁」。

### 介面

- **D8 群組標頭（`ReceiptGroupHeader`）**：
  - 已核對 → 以「已人工核對」（勾勾圖示＋文字，沿用「相符」的中性樣式）**取代**差額／無法判斷的警示與旗標；有備註時顯示備註。算術拆解不在標頭顯示（檢視頁仍有）。
  - 未核對 → 既有呈現不變；writer 多一個「標記為已核對」動作。
  - 任何狀態都有「查看整張收據」連結。
  - 已核對時 writer 可「取消核對」。
- **D9 標記流程**：點「標記為已核對」→ 小型對話框，可填一句備註（選填，≤ 200 字）→ 確認。樂觀更新，失敗回滾並 toast。取消核對不需確認（可立即再標回來）。
- **D10 整張收據頁** `/items/drafts/receipts/{receiptId}`：
  - 頂部：商家、日期、頁數、核對狀態與動作（同 D8）。
  - 算術拆解：品項合計、折扣、稅、運費、算術值、收據總額、差額——逐列對齊的明細表（金額 `tabular-nums` 右對齊）；缺值顯示「—」。舊快照（無 `balance_status`）只顯示有的欄位。
  - 品項行：桌面為表格，手機為收據行（hairline 分隔、無卡中卡，依 `DESIGN.md` §9）。每行顯示名稱、數量、單價、小計、狀態（待處理／已入庫／已捨棄／失敗，文字＋非色彩編碼）；已入庫且物品仍在 → 連到該物品。
  - 第一頁影像（`AuthImage`），附 D7 的說明。
  - 回到佇列的連結。
- **D11 互動狀態**：LOADING skeleton；`404` →「找不到這張收據」＋回佇列；其他錯誤 → 說明＋重試；影像載入失敗不影響其餘內容。
- **D12 權限**：viewer 進不了 AI 路由（既有行為，`403`）→ 頁面顯示既有的唯讀說明樣式，不渲染動作。
- **D13 視覺**：依 `DESIGN.md`——「已人工核對」是中性資訊，不用飽和色；差額警示維持既有的 `--warning`；色彩一律走 token。既有元件中的硬編 fallback 色值不擴散到新程式。
- **D14 i18n**：zh-TW／en 同步。

## 實作結果

### 實際完成項目

- D1–D5：新增 `AiReceiptReview`、Migration `0030`、schema 與收據 service；提供整張收據 GET、核對 PUT／DELETE。以本人任一狀態草稿判定擁有權；viewer 三端點皆 `403`，不存在／他人一律 `404`。原子 upsert 保留首次 `verified_at`，取消可重複呼叫。
- 整張收據包含全部六態、依行序排序；原始名稱／數量／金額與 AI 快照分開於人工核對。舊快照缺鍵補預設或 `null`；已軟刪除或不存在的物品不回傳連結。
- 佇列清單單次額外查詢取回當頁核對紀錄；process／accept／discard 單筆回應也帶正確值。已重新匯出 OpenAPI 並產生 TS 型別。
- D8–D14：標頭加入人工核對狀態、備註、標記對話框、取消動作及整張收據連結；核對操作同步樂觀更新所有佇列分頁與整張收據快取，失敗只還原核對欄位並 toast。
- 新增 `/items/drafts/receipts/{receiptId}`，包含算術明細、桌面表格／手機收據行、各狀態與物品連結、第一頁影像、載入／404／錯誤重試／viewer／缺快照與空行處理。沿用 UI 元件、currency formatter、設計 token，zh-TW／en 同步。
- `docs/ai.md` 補齊端點、核對語意及 D6／D7 限制；新增 API、元件、hook 與 stub e2e 測試，保留既有測試斷言。

### 與計畫的差異與實作取捨

- 設計範圍無變更；收據 service 獨立於既有草稿狀態機，核對不改寫 AI 快照、不寫稽核、不進備份。
- 物品沿用既有軟刪除機制，因此批次查詢仍有效的物品，避免只依賴 FK 而留下已刪除物品的連結。
- middleware 已涵蓋 `/items/:path*`，不需修改。i18n 既有「不得有未使用收據鍵」測試只擴充新元件來源清單，保留原斷言。
- 本機 server 被 sandbox 以 `listen EPERM` 拒絕綁定連接埠；改以實際元件輸出的 HTML 與專案 Tailwind CSS 做瀏覽器版面量測，這不等同 stub 端到端操作。
